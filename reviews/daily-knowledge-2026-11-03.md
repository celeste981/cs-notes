# 每日面试知识｜2026-11-03：Go map 什么时候需要同步？

> 主题：Golang 并发基础。本文是知识整理，不代表已经完成个人学习或口述验收。

## 问题

多个 goroutine 同时访问一个 map，什么时候需要加锁？

## 面试官考察点

- 能否区分并发只读、读写并发和写写并发。
- 是否理解读写必须遵守同一套同步规则。
- 能否根据访问方式选择互斥锁、读写锁或单一 goroutine 管理状态。

## 先讲人话

`map` 是按 key 查 value 的字典；`goroutine` 是 Go 的并发执行单元。

多人只读一本已经准备好的字典，通常可以各看各的；如果还有人在修改，就需要协调。锁像一本字典共用的访问规则，只有一部分人遵守是不够的。

## 再讲原理

普通 map 不内置并发同步。多个 goroutine 访问同一个 map 且存在写操作时，需要用锁或其他同步方式协调访问。完成安全发布、后续不再修改的 map，可以并发读取。[Go 官方 FAQ](https://go.dev/doc/faq#atomic_maps)

| 访问方式 | 处理原则 |
| --- | --- |
| 初始化完成，安全发布后只有并发读 | 可以并发读取 |
| 并发读和写同一个 map | 用同一套同步规则协调读写 |
| 多个 goroutine 并发写同一个 map | 协调所有写操作；不同 key 也不能直接当作安全 |

`Mutex` 是互斥锁；`RWMutex` 是读写锁。使用 `RWMutex` 时，读路径用 `RLock/RUnlock`，写路径用同一个锁的 `Lock/Unlock`。读锁只约束遵守该锁规则的访问，不会自动拦住直接写 map 的代码。[sync.RWMutex 官方文档](https://pkg.go.dev/sync#RWMutex)

## 面试怎么说

> 普通 map 不支持未同步的并发读写或写写。如果多个请求共享同一个可变 map，我会让读写遵守同一套同步规则，例如用 Mutex 或 RWMutex 保护；也可以由一个 goroutine 独占，再通过消息访问。如果 map 初始化完成并安全发布后始终只读，就可以并发读取。选方案时还要考虑一次业务操作是否包含多个步骤，不能只保证单次读取或写入安全。

## 生产场景

一个服务用 map 保存可动态更新的配置。请求处理代码读取配置，刷新 goroutine 更新配置。如果选择加锁，读取与刷新都必须使用同一个锁。

这是通用示例，不对应某个真实项目的个人贡献。

## 可展开追问

1. **所有请求都只读，还需要锁吗？** 初始化完成、经过安全发布且之后不再修改时，可以并发读取。先确认是否还存在后台刷新或其他写路径。
2. **只有读函数加 RLock，写函数直接赋值，为什么不够？** 写路径绕过了锁，读写仍可能同时发生；所有相关访问都要遵守同一套同步规则。

## 复习要点

- 先问“同一个 map 有没有写操作”，再讨论同步方式。
- 多个写操作即使操作不同 key，也不能直接并发写普通 map。
- Go 1.24 引入基于 Swiss Table 的 map 实现。`hmap / bmap / overflow bucket` 主要是旧实现的讲法，谈底层结构时先说明版本。[Go 官方说明](https://go.dev/blog/swisstable)

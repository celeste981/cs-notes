## 主题一：append 后，旧切片为什么可能看到元素变化？

### 先讲人话

slice 像一张记录数组位置与可见范围的便利贴。两张便利贴可以看着同一份数组，各自记录的长度却不同。追加结果存进另一张便利贴，不会自动改掉旧贴上的长度。

### 再讲原理

slice 描述底层数组的一段区域，包含指针、长度 len 与容量 cap。append 返回更新后的切片：容量足够时复用底层数组，容量不足时分配新数组。下面把返回值赋给 b，a 的长度仍为 1。

```go
package main

import "fmt"

func main() {
    a := make([]int, 1, 2)
    a[0] = 10
    b := append(a, 20)
    b[0] = 99
    fmt.Println(a, b, len(a), len(b))
}
```

| 初始设置 | 输出 | 原因 |
| --- | --- | --- |
| make([]int, 1, 2) | [99] [99 20] 1 2 | 容量足够，a 与 b 共享数组，b[0] 的修改可由 a[0] 看见 |
| 仅改为 make([]int, 1, 1) | [10] [99 20] 1 2 | 追加时容量不足，b 使用新数组，修改 b[0] 不影响原数组中的整数 |

### 面试怎么说

> 判断 append 的影响，先看容量是否足够，再区分切片描述和数组内容。容量够则复用数组，不够则分配新数组；把结果赋给 b，不会直接改变 a 的长度。共享数组时，对已有元素的修改可能互相影响。

### 可展开追问

1. b 追加到两个元素后，len(a) 会变成 2 吗？不会，返回的切片赋给了 b，a 的长度没有被重新赋值。
2. 分配新数组意味着任意元素都深拷贝了吗？不意味着。本例使用整数；若元素内部还引用其他对象，需要另行分析共享关系。

### 常见误区

把“长度没有变化”误认为“数组内容不会变化”；或依赖固定扩容倍数判断是否共享。本例只依赖容量是否足够的语义。

## 主题二：slice 传给函数，为什么元素变了，外面的长度没变？

### 先讲人话

传参像复印便利贴。函数和调用方各有一张，但开始时指向同一份数组。改共享数组里的已有元素，调用方能看到；只更新函数内部便利贴上的长度，调用方那张不会自动改变。

### 再讲原理

Go 参数按值传递。传递 slice 时复制的是切片描述，不是整段底层数组。下面先修改 s[0]，再把 append 的结果赋给局部变量 s；外部 a 的长度保持 1。

```go
package main

import "fmt"

func grow(s []int) {
    s[0] = 99
    s = append(s, 20)
    fmt.Println("inside:", s, len(s))
}

func main() {
    a := make([]int, 1, 2)
    a[0] = 10
    grow(a)
    fmt.Println("outside:", a, len(a))
}
```

输出：

```text
inside: [99 20] 2
outside: [99] 1
```

### 面试怎么说

> slice 传参也是值传递，切片描述会复制，底层数组仍可能共享。函数内修改已有元素可以影响调用方看到的内容；但把 append 的返回值赋给形参，只更新局部切片。需要让调用方保留追加结果时，可以返回更新后的 slice，再由调用方重新赋值。

### 可展开追问

1. 为什么 a[0] 变成 99？修改发生在 append 之前，此时 s 与 a 共享底层数组。
2. 如何让调用方保留追加结果？函数返回更新后的 []int，调用方用 a = grow(a) 接收；只在函数内给 s 重新赋值不够。

### 常见误区

把 slice 传参说成“传引用，所以外面的切片变量会一起变”。应分别判断切片描述与数组内容；还要看修改发生在 append 之前还是之后。

- [Go Slices：结构与共享](https://go.dev/blog/slices-intro)

## 主题三：读者用了 RLock，为什么还必须协调写路径？

### 先讲人话

map 是按 key 查 value 的字典；goroutine 是 Go 的并发执行单元。把锁 rw 想成门卫：读者向它登记，写者也向同一个门卫申请独占，才能安排等待。写者绕过门卫直接改字典，读锁就无法让这段写代码等待。

### 再讲原理

map 初始化完成、安全发布，且后续所有访问都只读、没有赋值或删除时，可以并发读取。只看请求函数不够，还要检查后台更新与清理。

RWMutex 是读写锁。已有读者持锁时，写者调用同一锁实例的 Lock 会等待；直接操作 map 不会自动检查这个锁对象。采用加锁方案时，相关访问都要遵守同一同步协议。

以下示例所有对 counts 的访问都通过这些函数，函数没有提前返回或其他分支：

```go
package counter

import "sync"

var rw sync.RWMutex
var counts = make(map[string]int)

func Get(key string) int {
    rw.RLock()
    value := counts[key]
    rw.RUnlock()
    return value
}

func Set(key string, value int) {
    rw.Lock()
    counts[key] = value
    rw.Unlock()
}

func Add(key string) {
    rw.Lock()
    counts[key]++
    rw.Unlock()
}
```

还要区分单次访问与完整操作。即使 Get 和 Set 各自正确加锁，Get 后加一再 Set，仍可能插入另一个请求：两个请求都读到 5，再分别写回 6，最终为 6 而非预期的 7。上面的 Add 让同一次持锁覆盖整个读取、加一、写回过程。这是根据互斥规则推导的交错示例，不表示每次运行都会丢失更新。

### 面试怎么说

> 锁只协调使用同一把锁的代码。共享 map 存在并发更新时，使用 RWMutex 的读者用 RLock，写者用同一实例的 Lock。写者直接操作 map 就绕过了同步协议。计数加一这样的复合操作，还需要让一次持锁覆盖整个读改写过程。

### 可展开追问

1. 读者使用 rwA.RLock，写者使用独立的 rwB.Lock，可以吗？不能靠两把独立的锁协调这些访问；它们不是同一锁实例。
2. Get 和 Set 分别加锁，为何仍可能丢失加一？两次调用之间已经释放锁，其他请求可以插入；应使用完整的 Add 操作保护读改写。

### 常见误区

- 认为 RLock 会让 map 的赋值语句自动等待。
- 只保护写入，读取或后台删除绕过同步规则。
- 把单次访问安全等同于业务复合操作完整。
- 只检查 map 容器，忽略其元素内部另有共享可变对象的情况。
